# Daily dispatch — dispatcher guide (NMWC)

Menu: **Daily dispatch**. Pick the **delivery date** (tomorrow by default) and the **depot**.

## 1. Upload orders
- Click **Choose the sales order file** and select the Excel or CSV exported from the sales system. The usual NMWC columns are recognised automatically (SO No, Req. Delivery Date, Customer Code, Branch, Item Code, Qty (Cases), Net Value, CM, …).
- Click **Check file**. Nothing is saved yet. You see: rows, customers, sales orders, **total cases**, new customers and new products, and any rows that need fixing.
- **Every order has a depot**: the file is for the depot picked at the top of the screen. On the old *Upload orders* page (it has no depot choice) the file goes to your company's only active depot; when your company has two or more active depots, that page refuses the file: upload it here, on **Daily dispatch**, after picking the depot.
- **One sheet of orders per file.** If an Excel workbook has order rows on more than one sheet (for example *Orders* and *LateOrder*), the check stops with *This workbook has order rows on 2 sheets: "Orders" (1,082 rows), "LateOrder" (116 rows). Nothing was read.* Save each sheet as its own file (a separate workbook or CSV) and check them one by one; a late sheet then asks for its late reason on its own. A workbook with one order sheet and other sheets (a cover page, notes, a customer list) is read from the order sheet, and the screen names the sheets it did not read. Only the order sheet counts towards the limit of 50,000 rows: a large customer list next to the orders does not stop the check.
- **File limits.** A file can be at most 10 MB and its order sheet at most 50,000 rows. An Excel workbook can also be at most 50 MB once unpacked (Excel files are compressed; a normal order file is well under 1 MB) and have at most 10 sheets. A file over a limit is refused at **Check file** with a message that names the limit, for example *This workbook has 12 sheets; at most 10 can be read.* Save only the order sheet as a new workbook (or as CSV) and check that. If the message says *the sheet goes on past row 50,100*, the sheet has many empty or formatted rows below the orders: delete those rows in Excel and check the file again.
- A few more limits stop unusual files that would make RouteIQ very slow: at most 200 columns on a sheet or in a CSV file, 2,500,000 cells in a workbook or CSV file (for example 50,000 rows of 49 columns, with the header row), links (hyperlinks) over at most 200,000 cells, at most 10,000 comments written by at most 1,000 people, and at most 1,000 metadata entries (a hidden part of the workbook). An Excel upload must be a real Excel workbook (.xlsx or the old .xls) or a CSV file: a web page or XML file saved with an .xls name, an OpenDocument (.ods) or binary (.xlsb) workbook is refused with a message; open it in Excel, save it as .xlsx and check that. A workbook with a chart sheet (a tab that holds only a chart) is refused too: delete the chart sheet, or save the order sheet as a new workbook, and check that. A chart placed on the order sheet itself is fine. The message always says what to do (for example *Delete the columns you do not need*, or *Remove the links*). Your usual order file is far below all of these. In a CSV file, empty columns after your data count as columns too: if a CSV is refused for its columns, delete the empty columns after your data in Excel, save it again and upload it.
- A large file takes some seconds to check (up to about 15 s near the limits); other people can keep working meanwhile. Your usual order file takes well under a second. If a file is refused with *This file takes too long to read* or *This file needs too much memory to read*, nothing was saved: delete the rows and columns you do not need (also empty rows below your data), or split the file into smaller files, and check it again. If you see *RouteIQ is reading other files right now*, wait a moment and check the file again. If you see *RouteIQ could not check this file*, nothing was saved: check the file again in a moment, and if it happens again, tell your administrator.
- If a row has an error (for example cases = "abc"), fix the file and check it again. Nothing is half-imported.
- **New customers are not errors.** They are created and marked **LOCATION REQUIRED**.
- If the orders are **late** (after 18:00 the evening before, or after a plan already exists), type the reason. The screen and the message say which: *Received after the 18:00 cutoff for …*, or *A plan (version 1) already exists for … (2 of its loads are dispatched)*.
- Click **Add … lines to the day**.
- **A file is added only once.** Lines already added (same delivery date, sales order, customer and product) are skipped, listed as *Already confirmed: …*. This is also the case when the customer (or product) has been deactivated since: the line says *Customer … is inactive now: its confirmed orders are not planned until it is reactivated*, not an error. Messages use the codes as they are in the customer and product lists, whatever letter case the file uses. Adding the same orders a second time — the same file again, a second browser tab, or an old checked file — is refused with a message and nothing is added. The same sales-order line with a **different number of cases** is an error: changing a confirmed line is not supported yet. Remove that row, and add the extra cases as a **late order without a sales-order number** (or with a new one); with the original number the late order is refused as well.
- **The same sales order and product on two rows** of one file are one line: the cases are added together, the line keeps the **highest priority** of the rows (P1 wins, also when the first row has none) and **every note**, whatever the row order. When the rows differ in priority, note or value, a warning names the rows. A value or margin blank on one of the rows makes the line's value unknown (never counted as 0).
- A checked file must be added within **24 hours**; after that, check it again. A file checked before this update that has the same sales order and product on two rows is refused at **Add**: check it again. If the depot of a checked file is deactivated before **Add**, nothing is added: reactivate the depot, or check the file again for another depot. If the cutoff passes or a plan is applied between **Check file** and **Add**, you are asked for the late reason at that moment.
- **Weights:** the weight column in a file is the kg of the whole line, and it is kept as it is. A weight of 0 counts as blank. A line without a weight (also a line added together from several rows when some of them have no weight) is weighed with the product's **case weight** and follows it: when a case weight is entered or corrected under **Products** (for example 1500 typed instead of 1.5), open orders get the new weight at the next **OPTIMIZE** or **RE-PLAN**. New products are created without a case weight. Only company admins can edit products: planners and supervisors ask an admin to add or correct it (see step 3).
- **Orders not delivered on earlier days** are listed in step 1 too, with **Bring forward to (the day)**: see *Orders not delivered on earlier days* below.
- **Deleting a file** (old *Upload orders* page) is possible only while none of its orders has been optimized. Once a plan was made with them, the delete is refused, so the plan keeps every order it was made for. **Orders that are in a plan cannot be removed in the app yet** (a cancel function is not built yet): a late order only adds orders and a re-plan plans the same orders again, so neither removes them. If a wrong file was planned, ask your RouteIQ administrator.

## 2. Resolve issues
Red cards need action before optimizing:
- **ADD LOCATION**: paste the customer's Google Maps link (a WhatsApp share link such as `maps.app.goo.gl/…` works) or `latitude, longitude`, click **Read**, check the pin, then **Save location**.
  - **Rule: every location must be correct. No item is delivered without one.** If the reading is not exact, the window says *This reading is not exact. Drop the pin on the customer's exact location, then save.* and **Save location** stays off. Click the map on the shop, or drag the pin there; then save. This happens when the link only shows the map area and not a pin (also an old link with `ll=`), when a directions link does not end at a point, when the coordinates have fewer than 4 decimals, when latitude and longitude look swapped, and when the point is outside Oman/UAE. The same when the text cannot be read (*This could not be read. ...*).
  - **Of the zeros at the end of a coordinate only one counts**, the same rule as the customer import (the owner's decision, 28 Sep 2026: "Same rule everywhere"). `23.5850, 58.4105` has 4 decimals and is fine; `23.5800, 58.4100` counts only 3, so the window says *Fewer than 4 decimals (only one zero at the end counts). Drop the pin on the customer's exact location.* and **Save location** stays off until you put the pin on the shop. A rough point copied from a cell formatted to show 4 decimals looks exact but is not. The same for coordinates written inside a link you paste (for example `?q=23.5800,58.4100`). If a real coordinate ends in 00, put the pin on the shop by hand.
  - **Rough coordinates searched in Google Maps stay rough.** If someone types `23.58, 58.41` into Google Maps and shares the result, Google's link carries those same rough numbers as its pin, and Google shows them as `23°34'48.0"N 58°24'36.0"E`. The link, the short link and that text are all not exact: the window asks you to put the pin on the shop by hand. A link to a real place (a shop or building Google knows) is read as before. Google drops the zeros at the end, so a searched `23.5850, 58.4105` also comes back with 3 decimals and needs the pin by hand.
  - If the point looks wrong, click the map to put the pin exactly on the shop.
  - Degrees, minutes and seconds work as Google copies them (`23°35'09.2"N 58°24'21.2"E`). Minutes and seconds must be below 60: `23°99'` is refused with the reason, never moved to another point. Whole degrees only (`23°N 58°E`, about 100 km) or no seconds (`23°35'N 58°24'E`, about 2 km) are not exact: put the pin on the shop by hand before saving. The same when the degrees, minutes and seconds are a rough pair written another way (`23°34'48.0"N 58°24'36.0"E` is exactly `23.58, 58.41`): the window says *These degrees, minutes and seconds are 23.58, 58.41 written another way ...*. About 1 real point in 1,300 looks like that too; put its pin on the shop by hand.
  - The window opens on the customer's saved pin. With nothing typed, **Save location** confirms that pin as it is, but only when it is exact and inside Oman/UAE (your company's delivery area). If it is not, the window says why (*This saved location is not exact*, *... is outside the delivery area and was never confirmed*, or *... has latitude and longitude swapped*) and **Save location** stays off: put the pin on the shop by hand. If the shop really is outside the area, RouteIQ asks once more (**Confirm & save**).
  - **Read** and **Save location** always belong to the customer the window is open for. If you cancel while a link is still being read and open another customer, the late answer is ignored; while a Read runs, pressing Enter again does nothing. Changing the text also cancels a Read still running.
  - **Save location** saves the point read from the text in the box. If you change the text after **Read**, the result turns grey (*Text changed - press Read*) and **Save location** stays off until you press **Read** for the new text. Text you typed but did not read is never saved (*Press Read to find this point before saving*). A pin you put on the map yourself can always be saved.
  - After **Confirm & save** for a point outside Oman/UAE, a new point (read again or put on the map) is asked about again.
  - The location is saved permanently. Tomorrow RouteIQ already knows this customer.
  - A directions link (`google.com/maps/dir/...`) is read only at the end of the route, and only when the end is a point. Its start can be your own position, so it is never read as the customer.
  - On the **Customers** page, a customer's page has **Set location**: it opens this same window, with the same rules. A customer whose saved pin cannot be used shows a red note there (for example *Saved location is not exact (low confidence)*), and the **Customers** list marks it **needs pin** and counts them at the top (*N need a pin*), so you can fix them before they have orders.
  - A red card *Saved location is not exact (low confidence)* means the saved pin is only a rough point, or a customer file put the customer somewhere else: use **ADD LOCATION** and put the pin on the shop. Until then its orders are not planned, and a load that already holds the customer cannot be locked, loaded or dispatched (step 3 then says the plan is out of date: **RE-PLAN**). The same for *Saved location is outside Oman/UAE and was never confirmed*.
  - After saving, the day and the plan below are refreshed straight away, no page reload needed. If the customer is already on a load and the pin moved more than 50 m, the stop shows the orange note (*Location updated after planning: new pin ...*), the load gets the **Changed after planning** badge, and the WhatsApp message and the driver sheet add a line *New pin - ask the dispatcher which one to use* with a link to the new pin (a message already sent or a sheet already printed does not change: send or print it again). The corrected pin does not stop the load: it can still be locked, loaded and dispatched, and the driver gets the new pin (the owner's decision, 28 Sep 2026). Only a stop still planned at a saved pin that was not usable (for example a red *Saved location is not exact (low confidence)* card) waits for **RE-PLAN** after you place the pin.
  - The plan itself still goes to the old pin: the stop's pin link, the route link and the map stay the planned ones until the load is re-planned. A **planned** load gets the new pin at the next **RE-PLAN**. A **locked** load must be unlocked first (a **loading** one goes **Back to locked**, then **Unlock**), then re-planned. A **dispatched** load keeps the old pin in the plan: tell the driver. A page reload shows the same. See *Changed after planning* below.

A red card **Customer is deactivated** means the customer was deactivated after its orders were added: its open orders are not delivered (they show as *unserved: customer deactivated*). Reactivate the customer under **Customers** and re-plan to deliver them. If the plan was made before the customer was deactivated, the card says its orders are **still on planned loads**: click **RE-PLAN** to take them off (or reactivate the customer). Orders already on locked, loading or dispatched loads stay there, and the card is not shown for them.

Below the cards:
- *No weight for N cases of …*: those products have no case weight, so truck payloads (kg) cannot be checked for them. Add the case weight under **Products**, or ask a company admin to (only admins can edit products).
- *Case weight entered or corrected under Products after these orders were added …*: it is applied to them at the next **OPTIMIZE** or **RE-PLAN** (orders on locked or dispatched loads keep the weight they were loaded with). If a plan is already in use, step 3 says the plan is out of date and **RE-PLAN** is enabled even with no new order.

**Only an admin can change a saved location.** You can add a location when a customer has none (or only one that cannot be used, a red card). Once a customer has a usable location, the button says **Location (admin changes)**: you can still open it and confirm the saved pin as it is, but moving it is refused with *Only an admin can change a saved location*. If the saved pin is not exact (for example a reading with too few decimals), it cannot be confirmed as it is: the dialog says *This saved location is not exact and only an admin can change it* - ask your company admin to drop the pin. If the pin is wrong, ask your company admin. A customer file you import also never moves a saved location (it still fills in customers that have none), and you cannot change the code or branch of a customer that has a saved location (orders find their customer by code and branch): ask your company admin. The same goes for two customers whose codes differ only in letter case (*C001* and *c001*): new orders go to one of them, so deactivating or reactivating one is refused when it would send them away from the one with the saved location (*Only an admin can deactivate this customer: new orders of its code would then go to ...*).

White cards are confirmations: priority (**P1 = highest**), customer type and receiving hours. They are optional while the loading rule is off. When the loading rule is on, receiving hours are not optional: a customer needs its own confirmed hours (or a delivery time for the order) before its load can be locked, so the list says so, and step 2 stays orange (not a green tick) with *N customer(s) miss data needed before loading*.
- **Receiving hours are confirmed or not.** Each card shows the hours in use: *(confirmed)* when you or an admin entered or confirmed them, *(not confirmed)* when they were saved but never checked, *(default - not confirmed)* when they are only the customer-type default. Hours you type in **Details** (on a card here, or on the customer's page) are saved as confirmed by you. If the customer accepts deliveries at any time, tick **Open all day**. If the hours shown are right, tick **These hours are confirmed with the customer** and **Save**.
- **Hard hours:** the customer cannot receive outside them, e.g. hypermarket 06:00–10:00.
- **Preferred hours:** nice to have.
- **Details** saves only what you change. Receiving hours are saved as a whole window: change the start or the end and both are saved as the dialog shows them, so check both before **Save** (if someone else changed these hours after your screen was loaded, yours replace theirs). A priority or unloading time that is still a default shows as a default: the priority list says *P3 - default, not confirmed* (pick a priority, P3 included, to confirm it), and the unloading box is empty with the default in grey. Pressing **Save** without changing anything confirms nothing.
- Times are **HH:MM** (06:30; 24:00 = midnight at the end of the day). A time such as 06:90 is refused with a message; nothing is saved.
- **Unloading time** is whole minutes, 0 to 480. Leave it **empty** to use the customer-type or Settings default; **0** means no unloading time at all. Text such as *10 min* is refused. Clearing a customer's own time puts it back on the default. This is the only way back to the default: a customer import can set a new time but cannot clear one (a blank cell keeps the time already saved).

**Delivery time for one order (urgent or promised).** Open **Delivery times** in step 2: every order of the day is listed with its customer's receiving hours. Click **Set time** on an order: the time starts from the customer's own confirmed hours; when the hours in use are a default or were never confirmed, the boxes are empty (a default never counts as a delivery window) and the dialog says so: type the time agreed for this order. Change it (for example 10:00 to 11:00, or only *To* for "by 10:00"), pick the reason (**Urgent**, **Promised to customer**, or **Other** with a short note; none is chosen for you) and **Save**. Saving the same time again changes nothing, and changing only the reason or the note does not make the plan out of date. This changes that order only; the customer's hours stay as they are. Then **OPTIMIZE** or **RE-PLAN**: the customer's visit is planned within that time, and the plan, the Excel file, the driver sheet and the WhatsApp message show **Promised 10:00–11:00**. With only *From* or only *To* ("from 14:00", "by 10:00"), the customer's own closing or opening time still applies on the other side (a shop that closes at 16:00 is never planned after 16:00); if the time you give is outside the customer's hours, the plan uses your time and warns you. All orders of one customer go in one visit: if two of its orders have times that do not overlap, the earliest is used and the plan warns you. **Use customer's hours** removes the time. A time set, changed or removed after the plan was made (also while the optimization was still running) is not in that plan: step 3 says the plan is out of date, and **Lock** is refused until you **RE-PLAN** - for every load of that customer, also a load holding another of its orders. A time removed again, so the order is as it was planned, needs no re-plan. An order already on a locked, loading or dispatched load cannot get a new time (unlock the load first).

**Loading rule is on** (an orange box in step 2, only when the rule is switched on in Settings): the customers of this day that miss a usable location or a delivery window. You can still **OPTIMIZE** and see the plan, but a load with one of them cannot be locked, loaded or dispatched until the data is in (see step 5). Customers whose orders are all on loads already locked, loading or out are not listed: those loads are never stopped by the rule. But an order split over two loads, one locked and one still planned, keeps its customer on the list: **Lock** of the planned load checks it. That order shows *on a locked load* and has no **Set time**, so confirm the customer's receiving hours in **Details**.

**Data to collect** (below **Delivery times**): customers with orders from today to the next days (3 by default) that miss a usable location or their own confirmed receiving hours, soonest delivery first. It shows the count for each depot (how many miss a location, how many miss hours) and this depot's customers, each with a link to its page. **Excel, this depot** / **Excel, all depots** give the list to whoever collects the data (see *Customer data: what to collect*); **Open on Customers** shows the same customers on the Customers page.

## 3. Optimize
- Click **OPTIMIZE**. RouteIQ asks how long the optimizer should search:
  - **Thorough - up to 20 min**: searches longer for a better plan and stops early once the plan stops improving. Suggested for a plan made **before** its delivery day (the evening plan for tomorrow). On a normal NMWC day it usually searches most of the 20 minutes, and has found plans with fewer trucks and loads than Quick.
  - **Quick**: the automatic search time for a day of this size, as before. Suggested **on the delivery day itself** (late orders, re-plans), so trucks are not held. A normal day (80-120 customers) takes about half a minute to a minute; bigger days get more search time, step by step: about 1.5-2 minutes at 150 customers, 3 minutes at 175, 4-5 minutes from 200.
  - The suggested choice is already selected; pick the other one if it suits better (for example Quick for a first look in the evening). **Cancel** starts nothing. **Re-plan** and a late order's *Re-plan now?* ask the same. The suggestion follows the clock when you press the button: a screen you opened the evening before and left open overnight suggests Quick in the morning, because the plan is then for today.
  - **Thorough on the delivery day** is possible, but the plan cannot be used before its search ends: its new loads are planned to leave no earlier than the start of the search + up to 20 minutes + the turnaround (for example *Planned from 09:50 (now 09:00 + up to 20 min Thorough search + 30 min preparation)*), and loading counts from the end of the search. If it first waits behind another Thorough search, its loads are timed from when its own search starts. Until it ends, the plan's loads cannot be locked or dispatched. The choice says so on the delivery day. When trucks are waiting, choose Quick.
  - No optimizer can promise the best possible plan. RouteIQ says how long it searched and why it stopped, for example *"Thorough search: searched 16 min (up to 20 min allowed); stopped when it stopped improving (no better plan for 8 min)"*, on the plan, in the job message and in the Excel (SUMMARY and ASSUMPTIONS). When no order could be planned at all (for example none fits on any truck, or no customer's hours can be reached), it says *search not run* and the unserved orders say why; when the search found no plan, it says that too. When you use another option instead (**Use instead**, for example MIN TRUCKS), the line describes that option's own search, which runs after the recommended plan's for up to its own time and does not stop early: *"The MIN TRUCKS option is in use. It searched for up to 1 min for its own goal (the fewest trucks), after the recommended plan's search (Thorough: 12 min of up to 20 min; stopped when it stopped improving)."*
  - The Excel ASSUMPTIONS sheet of a Thorough plan also lists **Route search - progress**: how the best plan's search score fell over time. It is a score, not money: it adds a large penalty for every stop not yet planned, so the first figures can be in the thousands. Each figure says how many stops were not planned yet, for example *0 s: 7226 (7 stops not planned yet); … 1 min: 179*.
  - While it searches the plan shows *Searching for the best plan - up to 20 min, stops early when it stops improving - 6 min so far*. You can leave the page: the plan is saved when the search ends. A **supervisor** (or company admin) can press **Use the best plan found so far** to end a Thorough search early: the plan found by then is checked and saved in about a minute (the other options are skipped); this is recorded in the audit log.
- Optimizing **today's** day during the day plans from now: no load leaves before now + the turnaround between loads + the loading time of its cases, and the plan says *Planned from ...* (see *Late orders*). Tomorrow's day starts at the first departure as usual.
- If some customers still have no correct location, you are asked whether to plan without them. Their orders become *unserved* with the reason (*location missing*, or what to fix). They are never put on a truck.
- If some order lines have **no weight** and a truck has a payload, you are asked the same way: **Cancel** and add the case weights under **Products** (planners and supervisors: ask a company admin, only admins can edit products), or **optimize anyway** — those lines then count as **0 kg**, so a load can be heavier than shown, and the plan keeps a yellow warning that says so. **Re-plan** asks the same question.
- One case heavier than every truck (usually a case weight typed per pallet or in grams) is not planned: it shows as *unserved: bigger than any truck* with *check the product weight*. The rest of that order is planned.
- A stop that would need more than 8 hours (480 min) of unloading is planned with 480 min and the plan warns about it; check the service time or split the delivery.
- **RE-PLAN without a new order:** step 3 also enables **RE-PLAN** when the plan in use is out of date: a case weight was entered or corrected for its orders, or a customer was deactivated while its orders are still on planned (not locked) loads. The plan view shows the same notes in yellow.
- **Priorities are strict:** one order of a higher priority always wins over any number of lower-priority orders (one P2 is never left out to fit eleven P3s). When the trucks really cannot carry everything, P5 orders are left out first, then P4, and so on.
- After the route search, RouteIQ re-checks which truck carries each load, so trucks do two or three loads each where the day allows instead of many trucks doing one short load. When this changed the plan you see a note such as *"Loads were re-assigned after the route search: 12 -> 5 trucks, 19 -> 14 loads, 720 -> 493 OMR operating cost."*
  - The re-check also tries to place orders the route search left out on free trucks or loads. When it does, the note ends with *"this also plans 2 stop(s) the route search had left out"*: loads and cost can then go up, because more is delivered.
  - **A second route search.** RouteIQ runs a second route search beside the main one, on the same orders, trucks and
    hours. Its plan goes through exactly the same checks, timing and costs as the main search's (the driver break and
    unloading finished by closing included), and it is used for an option
    only when it is clearly better for that option's goal (serving the higher priorities first; then, for Recommended, at
    least 1 OMR less total cost with the customer time preferences; for Min Distance at least 1 km less; for Min Trucks a
    truck or a load less, or 1 OMR less operating cost). Otherwise the main search's plan is kept. Such an option carries one
    note that says what got better for its goal, and shows the other figures that changed, for example *"A second route search
    found a better plan for this option than the main search: fewer km, 978.1 -> 974.2 km. Also changed: trucks 5 -> 6, loads
    14 -> 15, operating cost 529 -> 541 OMR. It passed the planner's own checks, timing and costs."* When the main search found
    no plan for an option and the second one did, its search status reads "plan from the second route search".
    Nothing else changes: review, lock, export and dispatch the plan as usual. It cannot see the early-arrival preference for
    P1/P2 customers (Settings), so its plans may deliver them a little later inside their receiving hours when that saves more
    than the preference is worth; the plan's cost already counts that preference.
  - Every load is then timed with the exact loading time between loads (Settings → Daily dispatch: timing). The route search only estimates it, so on a tight day with very full loads its plan may not fit. The lowest priorities are then left out until it does, with the note *"... stop(s) the route search had planned are left out: with the loading time between loads ... its loads did not fit the truck days"*. Re-plan, add a truck, or check the loading time.

## 4. Review the plan
- **Top row:** orders served, cases, trucks and loads, km, hours on the road and **paid** hours (each truck from its first departure to its last return), utilisation, fuel, cost, service % for P1–P5.
- **Operating cost** is the whole day: truck fixed costs, cost per load, km, fuel, the drivers paid for the whole truck day (the wait and turnaround at the depot between loads included) and overtime after the hours set in Settings. Hover over it for the parts. After a re-plan it includes the locked and dispatched loads kept from the previous version. A `*` means some loads were saved before this cost rule and keep their old cost (without depot time and overtime). The Excel **TRUCK DAYS** sheet gives the cost per truck.
- **Green bar:** *uploaded = planned + unserved*. If it is ever red, do not dispatch; report it.
- **Truck loads:** one row per truck and load (T01 · L1, T01 · L2 …) with departure/return, cases vs capacity and km. Click a row to see:
  - the **Loading manifest**: exact cases and kg per product for the warehouse; the kg add up to the load's kg, shown to 0.1 kg on the TOTAL line (a load may weigh exactly the truck's payload: weights are checked to 0.1 kg, with no margin). On an older version kept for the record, a product weight corrected later can make them differ, because the next re-plan re-weighed the orders. A line under the TOTAL then says so, for example *"The load was planned at 2,303.6 kg. Order weights changed since planning, so the products add up to 2,313.8 kg."* (the Excel load sheet says *MISMATCH ... order weights changed since planning*);
  - the **Delivery route**: DEPOT → customer 1 → customer 2 … → DEPOT, with ETA, receiving hours, cases, products and km.
- **Unserved orders:** every order that could not be planned, with the reason. *Rest of split* means the other part of that order is on a truck.
  - *Receiving hours cannot be met*, *Does not fit the shift*, *Bigger than any truck*, *Trucks out of loads*: a check proved the order cannot fit.
  - *Not planned by the optimizer - see reason*: the line under it says why.
    - *"Fleet capacity shortage ..."*: the trucks cannot carry every order today (more cases, or more kg, than all trucks and loads together), so lower priorities are left out first. It does not prove that this order is the one that cannot fit. On a heavy day it says *shortage by weight* or *weight is the tighter limit today*: then a re-plan cannot serve more, only another truck (or more loads per truck) can. The plan adds *more than the shortage alone explains* (in cases and kg) only when an unserved order would still fit the room left on a load, or on a truck that did not go out: then **Re-plan** or add a truck. Without that line, the room left on each load is smaller than any unserved order, so a re-plan cannot serve more.
    - *"Not planned: no load or free trip has room for its 1,600 kg ..."* (or its cases): no load of the plan and no unused trip has room for it, not even if the lower-priority orders on the loads were taken off (the reason then says *even with every lower-priority stop taken off*), and no other way of packing the loads could carry it (for example three orders of 1,600 kg on two 3,000 kg trucks with one load each). Add a truck or raise *Max loads per truck per day*. When the room is only spread over several loads, so that another packing might carry the order, it keeps the reason below instead. An order left out because of its receiving hours or the trucks' times keeps the reason below, even when lower-priority orders fill the loads.
    - *"Not planned: the optimizer found no truck, trip or time slot ..."*: nothing proves the order impossible. **Re-plan** to search again, add a truck, or raise *Max loads per truck per day*.
    - *"Not planned: once every load was timed with the loading time between loads ..."*: see step 3.
- **Split deliveries:** a customer whose day does not fit on any truck (cases or kg) is delivered in parts — each stop shows *Part 1 of 2*, *Part 2 of 2* and exactly which products and cases it carries. Parts can go on different trucks or loads. Turn this off in **Settings → Daily dispatch: timing** if you prefer such customers to be left unserved.
- **Plan options:** MIN TRUCKS (fewest trucks, then loads, then operating cost) and MIN DISTANCE (fewest km) are shown for comparison only. Every row is the whole day with that option: **Trucks** counts every truck used that day, including the trucks of locked, loading and dispatched loads; **Loads** are the kept loads + the new ones ("(9 new)"); **km** and **Day cost** are the kept loads' + the new loads' ("(new ...)" next to them shows the new loads alone), so the option in use shows the same trucks, loads, km and cost as the top row. Unless they serve more orders, they never need more trucks / km than the recommendation; when one plan is best on every measure, the options show the same plan. Click **Use instead** only if you really want one of them. The **Search** column says how long the route search ran and how it ended: *best plan found in the time allowed* is normal (the search is time-limited, so a plan is a good one, not a proven best); *search stopped at its limit* means a **Re-plan** may find a shorter plan.
  - **Why RECOMMENDED often costs more:** it also tries to deliver P1 and P2 customers early and inside their preferred hours (and, on a late-order re-plan, not to move orders to other trucks). MIN TRUCKS and MIN DISTANCE ignore that. **Preference cost** shows it in OMR (not money: the hover splits preferred hours, early delivery and moved orders). On a plan made before this version the figure is only the preferred-hours part, marked *(hours only)*, and the line below compares *preferred-hours cost*. **What it gains** says, in one line, what each option gains and gives up, for example *"vs MIN TRUCKS: P1/P2 delivered on average 40 min earlier, preference cost 19.5 OMR lower; but costs 35.4 OMR more, 87 km more, 1 more truck"*, or *"Same plan as RECOMMENDED"*. An option whose times break a rule (Timing checked is not Yes) is never called cheaper or better: it says *"Breaks the timing rules (N problems): it cannot be dispatched. Re-plan, or use another option."*, and nothing is compared with it. The Excel SUMMARY has the same lines under **PLAN OPTIONS**, with each option's timing check. If the cheaper option's later P1/P2 deliveries are fine for the day, **Use instead** is your call.

## 5. Lock, export, dispatch
- **Lock** a load when the warehouse starts preparing it. Loads of one truck are locked in order (Load 1 before Load 2).
- **Loading → Dispatch** when the truck leaves. **Dispatched loads can never be changed.**
- **A load never leaves without a driver** (owner rule 20). **Dispatch** is greyed out on a load without a driver (*Pick the driver first: a load never leaves without a driver*), and RouteIQ refuses it too: *T05 L1: a load never leaves without a driver. Pick the driver in the Driver list, or add a daily driver, then dispatch.* Pick the driver in the load's **Driver** list, or **+ Add daily driver…** (see *Daily drivers and hired trucks*). Lock and Loading do not need a driver.
- **Dispatch it when it leaves.** When a driver opens his page (the driver link) after a load's planned departure while the load is still *Locked* or *Loading*, the load row says so in amber, for example *T05 L1: driver page opened 07:15, load still Loading - planned departure 07:10. Dispatch it if it has left.* (the day screen's **Deliveries** card lists the same notes). Until you press **Dispatch**, the driver cannot record results for that trip, and his first arrival times wait on his phone.
- **Lock asks about a brought-forward order that may not be needed.** When an order on the load was brought forward from an earlier day and its result there was changed afterwards (for example the driver went back and delivered it), the stop shows a red *May not be needed: the 5 Oct result was changed after it was brought forward (to Delivered)* and **Lock** asks *... may not be needed ... Lock anyway?*. Check with the customer; Lock is never refused for it.
- **No load goes out to a customer without a correct location.** If a customer on a load lost its usable location after planning (for example a customer file put it somewhere else), **Lock**, **Loading** and **Dispatch** of that load are refused, and the message names the customers. Put the pin on each shop with **ADD LOCATION**, then **Re-plan**, so the stop goes to the new pin. A locked load must be unlocked first (a loading one goes **Back to locked**, then **Unlock**): a stop keeps the pin it was planned with until it is re-planned, so while the new pin is more than 50 m from the planned one, **Lock**, **Loading** and **Dispatch** stay refused until the re-plan. A pin you drop within 50 m of the old point (on the shop, a few metres from it) counts as the same place: the load goes, and a later correction of that pin is an ordinary one (the stop keeps its planned pin, and the sheets note the new one). To go without them, **Re-plan**: their orders are left unserved (unlock a locked load first).
- **Loading rule: no truck is loaded without a location and a delivery window for every customer on it** (when it is switched on in Settings, see *Customer data: what to collect*). **Lock** of a planned load is refused while a customer on it has no delivery window - neither its own confirmed receiving hours nor a delivery time its stop was planned with. The message names each customer and what it misses, for example *T01 L2: 1 customer on this load misses data needed before loading - C1 (Corner Shop): no delivery window.*, and says what to do: confirm the receiving hours in **Details** (on Daily dispatch or the customer page; or tick **Open all day**), or set a delivery time for the order under **Delivery times** and **RE-PLAN**. Confirmed hours count only when the stop was planned with them: if you confirm hours after the plan was made and they are not the hours the stop was planned with (for example the plan used the customer-type default), **Lock** says *... has confirmed receiving hours that its stop was not planned with ...*: **RE-PLAN** first. A load that is already locked or loading is never stopped by this rule: it goes to **Loading** and out as before, also when the rule is switched on after it was locked. A legacy run (from the previous planner) is not dispatched either while a customer on it has no delivery window.
- **Export Excel** gives the master workbook: summary, load plan, one sheet per truck load (manifest + route, printable), SKU loading summary, unserved, reconciliation, assumptions. It is there also when no order could be planned (no loads): the unserved sheet then lists every order with its reason. **Driver sheets (PDF)** only appear when the plan has loads. The assumptions sheet shows the settings the plan was made with, even after the settings changed, and says *not used in this plan* for a setting the plan did not use (for example the road time factor on a plan with straight-line distances). It also states the rules the optimizer used: a plan made before weights were checked to 0.1 kg says *earlier rule* on its **Weights** row, and its **Overtime** row does not claim the newer overtime rule.
  - The summary counts **Invoices (sales orders)** - how many are fully on trucks, partly (split) and not planned - and **Delivery orders**: one per customer branch, all its invoices of the day delivered together. So a day of 320 invoices to 200 branches shows 320 invoices and 200 delivery orders. **Stops on trucks** counts the customer visits (a split delivery is one stop on each truck).
  - Each truck-load sheet's **Notes** column has the customer's access notes (*Access: …*) and the order notes (*Note: …*), like the PDF driver sheet.
  - **Route search** says in words how the optimizer's search ended (see *Plan options*).

## Times not verified
Before a load is locked, loaded or dispatched, RouteIQ checks its truck's whole day: every load leaves only after the truck is back and loaded again (turnaround + loading minutes per case), every customer's unloading is finished by the end of its receiving hours (loads planned before this rule keep the earlier rule: unloading had to start by closing), no load is over the truck's cases or kg, the day fits the shift and depot hours, and a truck that works through midday has its driver break (see *Driver break*). The optimizer checks the same when it makes the plan (column **Timing checked** under **Plan options**).
- When a truck's day breaks a rule, the plan shows a **red box** with the reasons (for example *T01 load 2 leaves at 08:34, but the truck needs 50 min to reload and load 40 cases: ready 08:54*), the load rows say **Times not verified**, and **Lock**, **Loading** and **Dispatch** are off for that truck. Other trucks are not affected.
- Click **Re-plan** in the red box: the new version gets times that keep every rule (locked and dispatched loads stay as they are).
- If the problem is on a load that is already **locked** or **loading**, Re-plan alone does not fix it: a re-plan keeps that load exactly as it is. The red box names the load and says so. Put it back to Planned first (**Back to locked** if it is loading, then **Unlock**), then click **Re-plan**. If later loads of the same truck are locked too (for example after **Lock all loads**), they go back first, latest first: the red box lists them in that order, for example *put loads T01 L2, T01 L1 back to Planned first, in this order*. While every problem is on such a load, the red box's **Re-plan** is greyed out with the same list, because a re-plan would change none of them. This also applies when Re-plan is greyed out because every order is on a locked load.
- Its driver sheets, WhatsApp messages and workbook can still be sent or printed, but they say **TIMES NOT VERIFIED**: do not hand them out before re-planning.
- *Cases with no weight* (a yellow line) does not block: you accepted it at OPTIMIZE; add the case weight under **Products** and re-plan to check the payload. If the case weight you enter shows that a load is now over its truck's payload, that truck is blocked like any overload until you re-plan (unlock the load first if it is locked).
- A problem on a load that has already left is only shown, it never blocks the truck's next loads.
- With **Loading minutes per case** at 0 (the default) this practically never happens; it matters once the real loading minutes are entered.

## Changed after planning
A plan keeps the customer location, receiving hours, address and truck it was planned with, also on the driver sheets and in the workbook. If you correct a customer's location or hours (or a truck's capacity) after planning:
- the stop shows the change in orange (*Location updated after planning: new pin ...*), the load gets a **Changed after planning** badge, and the driver sheet and the WhatsApp message print the same line with a link to the new pin;
- a **planned** load keeps the old data until you **Re-plan** (step 3 says the plan is out of date, for a customer's location or hours and for a truck's capacity or payload); if a truck's capacity was lowered below what its load carries, the plan also shows a yellow line;
- a **locked** load: unlock it and re-plan to use the new location; a **dispatched** load keeps what the driver was given;
- if you move the **depot's** pin after planning, locked and dispatched loads keep the depot pin they were planned from (their times and km were planned from it): the map, the route links, the driver sheet and the WhatsApp message start and end there, with *Depot moved since planning ...*. Planned loads move to the new pin at the next **Re-plan** (step 3 says the plan is out of date). This is not like a customer's pin, where the driver gets the new one;
- driver names and phone numbers, and the customer's **access notes** (gate, forklift, receiver phone), are always the current ones: a note you correct reaches the driver sheet at once, without a re-plan.

## Driver sheets
Each driver gets one sheet per truck load: the stops in order with ETA and receiving hours, address and notes, cases per product, sales orders, a map link and QR code per stop, and a box for the customer to write the cases received, sign and stamp. The sheet never shows costs, fuel or margins.

**Assign the drivers**
- Set a **Default driver** for each truck once (menu **Trucks** → edit the truck). Every new plan puts that driver on the truck's loads.
- On the plan, each load row has a **Driver** list. Pick another driver for that load if someone else drives it (or **No driver**). Only active drivers are listed (add or reactivate them under **Drivers**).
- A driver you pick in the **Driver** list stays on that trip (the same truck and trip number) through every re-plan (late order, **Re-plan**, **Use instead**), even when the new times overlap one of their locked, loading or dispatched loads, or another trip you gave the same driver: the plan then shows the yellow warning, and you decide who drives which. (A trip RouteIQ filled in with that driver at those times gets another driver instead.) Under the list, such a driver reads **picked by hand**. If you have set that driver to inactive since, RouteIQ fills the trip in instead and says so in yellow.
- A driver RouteIQ filled in has a **Keep** link under the list instead, while you can change that load's driver (not once the load is dispatched, not while the plan is being optimized, and not for an inactive driver). Press **Keep** when you agree with that driver: it becomes your pick and re-plans keep it on that trip. (Choosing the same name again in the list does nothing.) A driver picked before the September 2026 update counts as filled in by RouteIQ until you press **Keep**.
- A re-plan or **Use instead** never changes the driver of a locked, loading or dispatched load.
- Every other trip RouteIQ fills in, starting with the trip whose time moved least: the driver the trip already had, else the driver of the same truck's nearest trip, else the truck's **Default driver** - the first of them who is active and not on another trip at that time. So when a re-plan moves one of two trips of the same driver onto the other's hours (or onto their locked, loading or dispatched load), the trip that moved gets the next driver in that order, or **No driver** for you to fill. Trip 1 and trip 2 of one truck can have the same driver. When two trips moved the same (or neither was in the plan before) and need the same driver, the truck that comes first by truck code gets the driver. A late order, **Re-plan** and **Use instead** decide the same trips the same way.
- A trip that lost or changed its driver is listed in yellow on the plan, for example *Driver changed by this plan: T02 · L1 (10:00–12:00) Ali → Sam, because Ali is on T03 · L1 at that time*, until you set a driver for that trip (another one, **Keep** to agree with RouteIQ's, or **No driver** if the trip has a driver); after that it is not listed again. If the plan left the trip with no driver (*... Ali → no driver ...*), the note stays until you pick a driver for that trip: choosing **No driver** there changes nothing. A trip that only got a driver (it had none) is not listed. **Use instead** also says how many driver notes the plan has; after a re-plan, look for the yellow notes on the plan. Check the drivers after every re-plan.
- If a re-plan or **Use instead** has no such trip for a driver you picked (for example **MIN_TRUCKS** leaves a truck out, or a truck gets fewer trips), the plan says so in yellow, for example *Driver picked by hand, not in this plan: you picked Bob for T03 · L1 (08:00–10:00), and this plan has no such trip. If a later plan has that trip again, pick the driver again.* RouteIQ does not put Bob back by itself: a later plan (or **Use instead** back to the first option) fills that trip in like any other, so pick Bob again if he should drive it.
- **No driver** is not kept through a re-plan: RouteIQ fills the trip in like any other (the driver of the truck's nearest trip, or the truck's usual driver), without a note, and never as your pick. To stop a driver being put back (for example, on leave), clear the truck's **Default driver** or set the driver to inactive under **Drivers**.
- If you pick a driver who is already on another truck at the same time, the plan shows a yellow warning and the driver list turns yellow. Pick another driver for one of the two loads. If a driver change cannot be saved (or its answer is lost), the plan is loaded again, so the list shows the driver RouteIQ has, or the plan says it may be out of date, with **Try again**.
- Once a load is **Dispatched**, its driver can no longer be changed.
- Save each driver's mobile number with the country code (for example `+968 9123 4567`). A local number such as `9123 4567` gets your country's code (+968 in Oman, +971 in the UAE) in the WhatsApp link; in other countries WhatsApp asks you who to send it to.

**Print or send**
- **Driver sheets (PDF)** (next to Export Excel) gives the sheets for all loads of the plan. Each load starts on a new page: print the whole pack and hand each driver their own pages.
- **PDF** on a load row gives only that load's sheet.
- **The driver link (QR) is printed first on every sheet** of the truck that day, with *Scan with the phone camera - opens in Chrome/Safari*: it opens the driver's own page (see *Driver link (QR) and the driver page*). The route QR codes follow (at most 2; longer trips keep their text links). Only dispatchers, supervisors and admins get the QR on the sheets: a sheet printed by a read-only user says *Driver link: ask the dispatcher*. A stopped link prints *Driver link stopped - ask the dispatcher*.
- **WhatsApp** on a load row opens WhatsApp with a short message for that load: truck and trip, departure, each stop in order with ETA, cases and map link, then the route link. If the driver has no mobile number saved, WhatsApp asks you who to send it to. When the truck has a driver link, the message also has *Your trips and delivery results: <link>*; when it has none yet, **WhatsApp** first opens the **Link** dialog, which makes the link and sends it. Check the message, then press send. **WhatsApp** is greyed out on a replaced plan version and while an optimization runs; a message copied from a replaced version starts with *REPLACED BY A NEWER PLAN - DO NOT USE*.
- On the sheet, **Route in Google Maps** (and the QR code at the top) opens the whole trip from the depot, stop by stop, and back. Long trips are split into parts, because a Google Maps link takes at most 9 stops between its start and end.
- A stop without a saved location says **No location - call dispatcher** and is left out of the route link.
- **Split deliveries** show *Part 1 of 2* and where the other part goes (truck and trip).
- A sheet is **void if a newer plan version is issued**: after a re-plan, print or send the new sheets for the loads that changed.
- The sheet prints Latin letters only. Text it cannot print (for example Arabic names or notes) shows as **[?]**, and the sheet says so: tell the driver, or also send the WhatsApp message, which shows the customer names in full.

The Excel workbook stays the dispatcher and warehouse file (loading manifests, costs, reconciliation); the driver sheets are for the drivers only.

## Driver link (QR) and the driver page
Each truck gets **one link per day** for all its trips: a QR code on the driver sheets, the **Link** action on each load row, and a line in the WhatsApp message. The driver scans it with the **phone camera** and his page opens in Chrome or Safari: the day, the truck, his trips in order with their status, and per stop the customer, a big **Navigate** button (Google Maps to the planned pin), the planned arrival and when unloading must be finished, the receiving hours or the promised time, the cases per product and per order, and the notes. English or Arabic (the button at the top). No account, no PIN and no app to install: daily drivers and drivers of hired trucks just scan.

- **Link** on a load row opens the dialog: the QR code, the link with **Copy**, **WhatsApp** (the link in English and Arabic to the driver's mobile), until when it works, *Last opened 07:15 · Used on 1 phone*, **Reissue link** and **Revoke**. Opening it makes the link when the truck has none yet.
- **It works until 12:00 the day after the delivery** (Muscat time). Results already saved on the driver's phone can still arrive for 3 more days.
- **Reissue link** when the driver changes or the QR was shared with someone it should not be: the old link stops at once. Print or send the new one. When a trip of that truck is on the road, the dialog asks first, because that driver's page stops too: send him the new link straight after.
- **Revoke** stops the link until you reissue it.
- **Used on more than one phone:** the dialog says *Used on 2 phones*. If one of them is not the driver's phone, reissue the link.
- **You changed the driver of a truck whose link was made for another driver:** RouteIQ asks *The driver link for T05 on 5 Oct was made for Salim. Reissue it for Khalid? Printed sheets and WhatsApp messages already sent for T05 stop working: print or send again.* **Keep link** (the default) keeps the old link working. It does not ask when the link was made before any driver was set (it then takes the new driver), when you change a later trip, or while another driver is on the road with the link.
- **One link per truck, several drivers:** when a truck has a different driver on different trips, the one link covers all its trips; whoever holds it records for the truck. The dialog says so.
- **Opened inside Facebook, Instagram or a QR app:** the page shows *Open in Chrome* (Android) or how to open it in Safari (iPhone), because those apps often block the location and the camera. Tell drivers to scan with the phone camera.
- **Location:** the page says on first open that it uses the phone's location only while it is open, to start the stop timer and to record where delivery photos are taken, and never keeps a track of the route.
- If you open a driver link while signed in to RouteIQ, the page says *You are signed in to RouteIQ as Ali: results are recorded as the office.* (A read-only user cannot record anything there.)

### What the driver does on his page
- **Start deliveries** (a big green button, from 30 minutes before the first trip leaves): the phone asks once to use the location. From then on the page starts the **stop timer by itself** when the truck stands at a customer (about 20 seconds inside the arrival radius) and notes when it leaves. Tell drivers: *keep the page open; if the screen locks, the timer may pause*, and *when you arrive, open this page again* after using Navigate.
- **I have arrived** is always there for a stop the timer did not catch (location off, a wrong pin, a customer next to the depot).
- **Arrived at ACME - when?** When the page is opened already at the shop, it asks when he arrived (*Now*, *5 / 10 / 15 min ago*). Such arrivals are kept but marked *not observed*: they never count as measured unloading times.
- **Which customer are you at?** Two customers inside the radius together (one building, two branches at one pin): he picks one.
- **The result** of each stop: **Delivered**, **Partly** (cases delivered per product line, then the reason) or **Not delivered** (the reason: *Shop closed*, *Customer refused*, *No one to receive*, *Wrong location or could not find*, *No time left*, *Payment issue*, *Damaged goods*, *Missing from the truck*, or *Other* with a note). A **photo** is needed for Delivered and Partly when *photo required* is on (up to 3); *Camera not working* lets him save without one, and the result says so. He can **Change result** or **Undo result** until the trip is completed, but not once its order was brought forward to another day.
- **Back at depot** after the last stop of a trip. When every stop of the trip has a result, RouteIQ marks the load **Completed** by itself (the audit log names the driver link); otherwise the load stays *Dispatched* and the page says *The trip closes when every stop has a result.* Your **Completed** button works as before.
- **Weak signal:** everything is saved on the phone first and sent when there is signal; the header shows *Waiting to send (3)*, *No signal* or *All sent*. Nothing is sent twice. Results saved offline show *Saved on phone - waiting to send*. If you change a result from the office, his page shows *Changed by office / another phone*.
- **Arrivals before you press Dispatch** are kept on his phone and sent once the load is dispatched; results can only be recorded on a dispatched trip. So: **dispatch the load when it leaves.**
- **After the link stopped** (reissued, revoked): his page lists the results that were not sent, so he can show them to you. After the day is over, results saved before the link expired can still arrive for 3 days; they show as *recorded after the trip closed* and never change a result that was there when the trip was completed.
- The results appear at once on the plan screen, on the day screen's **Deliveries** card and in **Bring forward** (see *Delivery results*). A short guide to give to drivers (English and Arabic) is in `docs/DRIVER_GUIDE.md`.

## Daily drivers and hired trucks
- **Daily (casual) driver:** in a load's **Driver** list choose **+ Add daily driver…**, type the name and the mobile (with the country code), and **Add and put on this load**. The driver is saved as a daily driver (code `DAY-261005-1`, no account) and listed as *Salim (daily)*. If the mobile is already saved for a driver, RouteIQ asks *This phone belongs to daily driver Salim. Use Salim?*: **Use Salim**, or **Change the phone**. Typing the same name and mobile again uses the same daily driver.
- On the **Drivers** page daily drivers have a *Daily* badge and a filter. A company admin can make one a regular driver (edit, switch off *Daily driver*).
- **Hired trucks:** a company admin adds the hired truck under **Trucks** with **Hired from outside** switched on, and deactivates it when it goes back (every active truck is planned every day). The plan shows *hired* next to the truck, the sheets *HIRED TRUCK*, and the driver page *Hired truck*. Its driver is usually a daily driver; the driver link works for any truck.
- **Old daily drivers are tidied up by themselves:** a daily driver who has had no load for 30 days disappears from the Driver list (adding the same mobile again brings him back), and his mobile number is erased after the time driver positions are kept (Settings, default 90 days). His name stays on old plans and in the audit log.

## Delivery results
What the drivers record on their page reaches the office at once (the plan reads it again every minute while a load is on the road). Nothing here changes a plan by itself.

**On the plan (Truck loads).** A load that left shows its progress in the **Status** column: *Delivered 7/12*, *2 partly*, *1 not delivered* (red), *2 no result* (amber), and *Back 14:32* when the driver tapped Back at depot. Open the load: the stop table has six more columns.
- **Result:** *Delivered*, *Partly 34/40* or *Not delivered*, the reason (*Shop closed*, *Other - gate locked*, ...), who recorded it (*by driver*, or *by Ali (office)*), *→ 6 Oct* when its cases were brought forward, and these notes:
  - *recorded after the trip closed*: the result reached RouteIQ after the load was completed (a phone without signal); it never changes a result that was there when the trip was completed, and Bring forward never ticks it by itself;
  - *no photo: camera failed (driver)*: the driver tapped *Camera not working*; *no photo (office)*: recorded by the office without a photo;
  - *changed after it was brought forward*: someone tried to change the result after its cases were brought forward; the change was refused (see below).
- **Arrived:** the time, and *manual* (the driver tapped *I have arrived*, or answered *Arrived when?*), *set by office*, *arrival not observed (page opened at the shop)* (the page found the truck already at the shop, so the real arrival was earlier) or *far from pin* (the phone was far from the pin: counted as manual).
- **Left:** the time, and *result time* (no departure was seen - the page was closed or GPS was lost - so the result ended the stop) or *not observed* (the page was away when the truck left: the time is the last moment it was seen at the shop).
- **Unload:** *plan 20 / actual 34 min*. The actual minutes count from the window start when the truck waited for the shop to open. *unverified timing*: the phone's positions look wrong (for example exactly on the pin, or the same accuracy again and again); such a stop is left out of measured times and the on-time figure.
- **Photos:** *2 photos* opens the photo viewer: the picture, when it was taken, *38 m from pin* (or *no location: location off / timed out / poor signal*), and *taken earlier (before the arrival)* for a photo older than the arrival (a gallery photo). *1 not received yet*: the result named a photo that is still on the phone. A photo removed by the retention says so.
- **Record** (dispatchers and up): record or correct the result of any stop of a load that left - a driver without a phone, a forgotten stop, a wrong tap. Choose **Delivered (all)**, **Partly delivered** (the cases delivered per product, then why the rest was not) or **Not delivered** (the reason; *Other* needs a note), optionally **Arrived** and **Left** (HH:MM), and **Save**. It is recorded with your name, as the office, and the audit log keeps the result before and after. **Clear result** removes the result (the stop then counts as delivered with no result). The driver sees *Changed by office / another phone* on his page. When a load is back at the depot and this was its last stop without a result, the load becomes *Completed*.
- **A correction after Bring forward.** When the cases of a stop were brought forward to another day and your correction would make them fewer (for example the customer found the cases: *Delivered*), RouteIQ refuses it: *These cases were brought forward to 6 Oct and that copy is not planned yet. Undo the bring forward to record this result.* Click **Undo the bring forward and record this result**: the copy on 6 Oct is removed and your result recorded, together. When 6 Oct is already planned with that copy, it cannot be removed in RouteIQ yet: the message says so (ask an administrator to remove the copy), the stop shows *changed after it was brought forward*, and 6 Oct's stop warns *May not be needed*. A correction that makes the shortfall bigger is simply recorded (Bring forward then lists the extra cases, see below).

**On the day screen (Deliveries card, under the plan).** *212 of 300 stops have a result · 196 delivered in full · 9 partly · 7 not delivered · 88 no result yet*, the reasons with their cases (*Shop closed 4 stops / 160 cases*), *Arrived inside the window 91 % (of 140 observed arrivals)* (only arrivals the page really saw, typed in, or set by the office; an early truck that waited for the shop counts as inside), *No photo: camera failed 3 · Recorded after the trip closed 1*. Then **Back at the depot, no result recorded (counted as delivered)**, per truck, with **Record** next to each stop, and the late-dispatch notes. **Delivery actuals (Excel)** downloads the day: one row per stop of a load that left - planned against actual arrival and unloading, inside the window or not, the result and reason, cases delivered and not, photos and distances, who recorded it - with a Summary and a Reasons sheet. (The Excel covers at most 31 days; it has no money.) A day before the delivery results started says *Delivery results started on 5 Oct*.

**Dashboard.** A **Deliveries** tile shows the last 7 and 30 days: delivered in full, arrived inside the window, not delivered by reason, no result recorded.

**Measured unloading time.** Once a customer has at least 3 visits timed automatically, its **Details** dialog on Daily dispatch says for example *Unloading: 20 min planned · measured 34 min (median of 7 timed visits, 12 Sep - 3 Oct)*. **Use measured time** puts the measured minutes in the unloading-time field; **Save** keeps them (as confirmed). The **Customers** page has the same in an *Unloading* column (its **Use measured time** asks first, then saves). Only visits timed by the page itself count (not arrivals typed in, found when the page was opened, unverified, recorded after the trip closed, across the driver break, or far longer than planned), measured from the window start, and without the per-case part, so it compares with the planned base time. Nothing changes by itself.

**Pin may be wrong (company admins, Customers page).** A yellow box lists customers whose delivery photos (else the driver's tapped arrival or result) were more than 150 m from the pin on 2 of their last 3 visits, or where the driver said *Wrong location or could not find*: the distances with dates and a **suggested point** (opens in Google Maps). Check it, open the customer and use **Set location**. No pin moves by itself; only a company admin changes a saved pin, as before.

## Late orders (e.g. a P1 customer calls at 22:15)
- Click **Late order** on the plan (or upload a small file in step 1), enter the customer, products, priority and reason (why it is added after the cutoff, or to a day already planned).
  - A sales-order line that is already on the day (same sales order and product) is refused: enter only new lines. For **extra cases** of a line already added, leave the sales-order number empty, or use a new one.
  - A deactivated customer or product is refused: reactivate it, or use another code.
  - A new product has no case weight yet: add it under **Products** (or ask a company admin) before re-planning, or the re-plan asks before counting it as 0 kg.
  - *Another order file or late order is being added right now*: nothing was saved; try again in a moment.
- Click **Re-plan**. RouteIQ creates **plan version 2**:
  - locked, loading and dispatched loads stay exactly the same;
  - the late order goes into a free future load, another truck or an extra load, or is shown as *unserved: late order – no capacity*;
  - the blue bar tells you what changed.
- **Re-planning today starts from now.** When you optimize or re-plan the day you are in (Muscat time), no new load leaves the depot before **now + the turnaround between loads** (30 min unless your admin changed it). The plan says so in a yellow note, for example *Planned from 09:30 (now 09:00 + 30 min preparation)* (other notes, such as weights or drivers changed, can be above it), and the Excel ASSUMPTIONS sheet has a *Planned from* row.
  - **Loading starts now too.** When your company sets a loading time per case, a new load also waits for the loading of its own cases from now, on every truck: a truck that stood at the depot all morning is timed exactly like one that just came back. For example at 09:00, with 30 min turnaround and 0.05 min per case, a 700-case load leaves at 10:05 at the earliest, whichever truck carries it. The yellow note gives an example for a full truck.
  - This also holds when you plan today early, before the first departure: at 05:15 with a 06:00 first departure, a full truck may leave after 06:00. The plan then says *Planned on the delivery day at 05:15: loading starts now ...*.
  - Locked, loading and dispatched loads keep their times. A truck that is still out leaves again only after it is back and turned around (for example back at 09:57: not before 10:27, plus loading time).
  - A customer whose receiving hours end before any truck can get there from now is shown as *unserved: no truck can reach this customer inside its receiving window* with the earliest possible arrival.
  - If now + the turnaround is at or after the depot's closing time, no new load can leave today. The yellow note says so, and every open order is *unserved: does not fit the shift* with the reason *Planned on the delivery day from 18:15: the depot closes at 18:00, so no new load can leave today.* (not a truck busy with locked or dispatched loads).
  - **Before you re-plan during the day, mark every load that has left as Dispatched.** A load still *Planned* in RouteIQ is planned again from now, even if the truck has already gone.
  - The time is taken when you click; a plan for tomorrow is not affected, whatever the time.
- Older versions stay under **Plan versions** (read-only).
- A late-order re-plan keeps the other orders on their trucks where it can, so drivers and loading are not reshuffled for one order.
- **Re-plan** (on the plan, or **RE-PLAN** in step 3) with no late order waiting is a full re-optimize: RouteIQ looks for the best plan for everything not locked, even if that moves orders to other trucks. Lock the loads the warehouse has started first, and send new driver sheets for the loads that changed.
- **Nothing to plan:** when every order is already on a locked, loading or dispatched load (and nothing is unserved or waiting), **Re-plan** is greyed out and step 3 says *nothing left to plan*. To change a load, unlock it first (a dispatched load cannot be unlocked; for more orders on that day, add a late order).
- **If the optimization fails** (optimizer down, out of time, a system update during the solve, the planner busy or restarting), the new version shows *Optimization failed - previous plan kept*: its loads are the previous plan, and you can lock, load and dispatch them as they are. Only locked and dispatched loads are marked *kept*; the others are the previous plan until the next optimization. Weights entered under **Products** since are not applied yet: the plan still warns about them. Click **Re-plan** to try again.
- **A plan stuck on "Optimizing…"** (it does not move for many minutes, often after a RouteIQ update during the optimization): the plan shows a yellow line under *Optimizing…* that says what happened.
  - *"... its optimization has already ended"* (or *"... no optimization is running for it"*): RouteIQ puts the plan back by itself within a minute. Until then **OPTIMIZE** and **Re-plan** stay greyed out; you do not need to reload, the screen then shows *Optimization failed* and both work again. A **supervisor** (or company admin) can press **Reset stuck plan** to do it at once.
  - *"This optimization stopped without a result (the server restarted while it ran)"*: RouteIQ fails it by itself within a few minutes. A **supervisor** (or company admin) can press **Reset stuck plan** now; after that, optimize or re-plan again. The reset is recorded in the audit log with who did it.
  - A reset plan shows *Optimization failed*. A re-plan version keeps the loads it holds (the previous plan): lock, load and dispatch them as usual.
  - **Reset stuck plan** is refused while the optimization is really running on the server (*"still running"*) or showed a sign of life less than 2 minutes ago: wait for it; it ends by itself (a Quick search at most 10 minutes after it starts, a Thorough one at most 22).
  - A long Thorough search is not stuck: *Searching for the best plan - … - 12 min so far* keeps counting. If RouteIQ is updated during the search, the optimization fails: at once with *The server was restarted (an update) during this optimization. Nothing was saved - optimize again.* where the server is set up for it, otherwise within a few minutes - first the plan shows *This optimization stopped without a result (the server restarted while it ran)* (a supervisor can **Reset stuck plan**), then it fails with *No sign of life for 5 minutes: ...*. Either way nothing was saved: click **OPTIMIZE** (or **Re-plan**) again.
  - If someone else started an optimization of the same plan a moment before you, yours starts nothing: the message says so, and which search (Quick or Thorough) is running, for example *An optimization (Quick) was already running for this plan, so your choice (Thorough) was not applied*. When it ends, re-plan if you still want the other search.
- While an action runs (a lock, **Lock all loads**, **Use instead**, **Re-plan**, a late order's **Re-plan now**, or step 3's **OPTIMIZE / RE-PLAN**), the other buttons wait for it, until the screen shows its result. If two people change the same plan at once, one of them may see *Plan is being saved - retry in a moment*: nothing was changed, just click again.
- If the connection drops (or RouteIQ is being updated) while you click, you see *The server could not be reached*. The plan stays on screen (it may be out of date) with **Try again**; if the day could not be loaded either, the day shows **Try again** at the top. When the connection is back, click **Try again** (it is off while a reload or another action is still on its way): the screen then shows whether your change was saved, and the buttons work again. Click again if the change was not saved. A late order you are typing and the loads you opened stay open when the day comes back after a lost connection.
- An option that found no plan shows *No plan* instead of **Use instead**.
- **Busy optimizer:** one Quick and one Thorough optimization per company can run at the same time (with the standard settings), so tomorrow's Thorough plan never holds up a Quick re-plan of today: the re-plan waits only for another Quick one. A second Thorough search waits for the first. Up to two more of each kind wait (*Queued: other optimizations are running*) and start on their own, in the order they were queued; Thorough plans waiting never take the places of a Quick re-plan. A further one of the same kind is refused with *Your company already has 2 Quick optimization(s) waiting* (or *2 Thorough ... or choose Quick*): try again once one has started. When the optimizer is very busy with other companies, a second one of the same kind may be refused with *The route optimizer is busy with other plans* while your first one waits; your first one of each kind is always queued, so tomorrow's Thorough plan waiting never gets today's Quick re-plan refused. After many optimizations in one hour RouteIQ asks you to wait a few minutes.
- **Planner busy or restarting:** if the optimizer cannot get ready to search, or cannot go on searching (for example while it restarts, or when its server is short of memory), the optimization stops within seconds with *The planner is busy or restarting - try again in a minute. Nothing was changed.* Nothing was planned or saved: a plan you already had stays exactly as it was (the screen says *Optimization failed - previous plan kept*, and its loads can be locked, loaded and dispatched as usual). Wait a minute, then press **OPTIMIZE** (a day without a plan yet) or **Re-plan** (a plan in use) again. RouteIQ records this for an administrator (in its logs and its health check), but nobody is called or messaged automatically: if it happens again after a minute, tell your administrator.

## Orders not delivered on earlier days (Bring forward)
An order that was not delivered on its day does not move to the next day by itself. **Bring forward** does that, when you decide.

**What counts as not delivered.** For the depot on screen, RouteIQ looks at the orders of the **7 days before** the day on screen - never a day after today - and lists every order with cases that were not delivered:
- **Unserved** in the plan of its day (for example *no truck had room left*);
- **Load never left**: on a load of its day's plan that is still *Planned*, *Locked* or *Loading* (it never left the depot);
- **Never planned**: its day was never planned, or it was added after that day's plan was made and not re-planned;
- **Not delivered** (delivery results): on a load that left, the driver (or you, with **Record**) recorded *Not delivered* or *Partly delivered*. The reason says what was recorded and by whom, for example *Not delivered: Shop closed (driver)*, *Partly delivered: 6 of 40 cases not delivered: Damaged goods (dispatcher)* or *Not delivered: Other - gate locked (driver)*, and the stop (*T01 L1 stop 3*). Only the cases not delivered are listed.

Other orders on **dispatched** or **completed** loads count as delivered and are never listed - also a stop with **no result recorded** (it is listed below the list for information, see *No result recorded*). **Mark every load that left as Dispatched** (and Completed) first, or RouteIQ lists its orders as not delivered. For a split delivery only the part that did not leave (or was recorded as not delivered) is listed, for example *40 of 100* cases.

**Today's orders recorded as not delivered** are ticked by themselves only when the result is settled: every open case was recorded as not delivered, every part of the order that left has a result, and **the truck is back** (the driver tapped *Back at depot*, or the load is *Completed*). Until then the row says why it is not ticked: *truck still out, the result may still change* (the driver may still go back and deliver), *other part (T03 L1 stop 1) has no result* (a split delivery), or *recorded after the trip closed*. Earlier days are ticked as before, except a result *recorded after the trip closed*, which you tick yourself if it is right.

**Today's orders (planning tomorrow in the evening).** When the day on screen is later than today (the day screen opens on tomorrow), today's orders that were not delivered yet are listed too - on a load of today that has **not left yet** (*Planned*, *Locked* or *Loading*, also one loaded last night), **unserved** in today's plan, or **not planned yet** - in a group of their own at the end of the list: **Today (27 Sep) - may still leave today**, with the warning *Today's loads that have not left yet may still go out today; tick only orders you know will not be delivered today.* They are **not ticked**: tick only the ones you know will not go out today (for example in the evening, when today's last trucks have left). Their reason says *Load not left yet* or *Not planned* (today is not over). Orders on dispatched or completed loads of today are never listed. The question before you bring them forward, and the message afterwards, say how many of today's orders you picked.
- A brought-forward order of today is closed on today, exactly like an earlier day's order: today's plan stays as it was, for the record.
- A load of **today** that still holds one **cannot be locked, loaded or dispatched** (it would be delivered twice). The message on the load (also on the plan version page) says what to do: **re-plan today** to plan its other orders without them, or **unlock** the load (put it back to Planned) - if it was loaded, unload those cases first. A *Loading* load has no **Unlock** button: click **Back to locked** first, then **Unlock**. If a later load of the same truck is locked or loading, unlock that one first.
- Today's orders are never brought forward to today itself, and orders of a day not due yet (tomorrow or later) are never listed. **Look again** reads the list again (today's loads may have left meanwhile).

**Only to today or a later day.** Orders are brought forward to the day on screen only when that day is today or later. When you open a day that is over (to look back), the box is not shown.

**How to use it**
- In step 1 a yellow box says *Not delivered on earlier days: 12 order(s) (840 cases)*, and, when today's orders are listed, *Today (27 Sep): 3 order(s) (62 cases) not delivered yet* with the warning. **Show list** gives each order: customer, the day it was due, the cases and why it was not delivered; today's orders come last, under their own heading.
- All orders of **earlier days** that can be brought forward are ticked; **today's are not** (see above). Untick the ones you do not want (for example an order the customer cancelled, or a load that really left but was not marked Dispatched). What you ticked or unticked **stays** when the list is read again (after a message that the list changed, after bringing some orders forward, after an OPTIMIZE or RE-PLAN of the day, after **Look again**); only orders that are new in the list get the default (ticked for an earlier day, not ticked for today). Check the count on the button before you click: it also says how many of today's orders are ticked.
- Click **Bring forward to (the day)** and confirm. The orders become orders of the day on screen: same customer, branch, sales orders, products and weight per case, with only the cases not delivered. Their **priority stays as it was** (it is not raised).
- **No plan yet for the day:** **OPTIMIZE** plans them with the other orders.
- **The day is being optimized right now:** the button is off until it finishes. (If orders were brought forward meanwhile, for example by a colleague, they are not in that optimization: **RE-PLAN** adds them when it finishes; the message says so.)
- **The day already has a plan** (for example loads locked and loaded the night before): they wait like late orders. Step 3 says *... brought forward from earlier days*; click **RE-PLAN**. Locked, loading and dispatched loads stay exactly as they are; the brought-forward orders go on the other loads, or are *unserved: late order - no capacity* when nothing is left.

**Where you see them**
- On the day they were brought to: the list *brought forward from earlier days* in step 1, the badge **Carried over from 27 Sep** on the stop in the plan (the day the order was first due), *CARRIED OVER from 27 Sep* on the driver sheet and on the Excel truck-load sheet, and a **CARRIED OVER** part on the Excel SUMMARY.
- On their own day: they are no longer open, unserved or waiting there (the dashboard counts them on the new day). The plan of that day stays as it was, for the record: its stop or unserved line says **Carried over to 28 Sep**, and a load that still holds such an order cannot be locked, loaded or dispatched (it would deliver them twice).
  - A **Planned** load that holds **only** brought-forward orders was never loaded: **leave it as it is**. It stays in that day's plan for the record.
  - A **Locked** or **Loading** load that holds **only** brought-forward orders **was loaded** (for example the night before) and never left: its cases are on the truck, but they are planned on the new day now. **Unload them back to stock, or tell the warehouse, before the new day's loads are picked**, so they are not loaded twice; then put the load back to Planned. It stays in that day's plan for the record. Step 3 of that day and the message on the load say the same.
  - When nothing else of that day is open, a **RE-PLAN** has nothing to plan and says so (the Re-plan button is off); Step 3 never asks you to unlock such a load.
  - A load that also holds other orders: put it back to Planned (if it is locked or loading, unload the brought-forward cases first) and **RE-PLAN** that day; the other orders are planned again, the brought-forward ones are left out.
  - The part of a split delivery that was **dispatched** was delivered: it shows no *Carried over* mark, on the plan, the driver sheet or the Excel. Only the part that did not leave was brought forward.
- The **Orders** list (old *Upload orders* page) shows the original as **carried over to 28 Sep** and the copy with **Carried over from 27 Sep**; its totals count the cases once.

**Not brought forward** (listed, without a tick, with the reason):
- the customer is **deactivated**: reactivate it under **Customers** first;
- the same sales-order line is **already on the day** (it was entered again, for example in the next day's file): nothing is added twice. Check which one is right;
- the same sales-order line was **entered again for a later day** (same sales order, customer and product, in any depot): only the newest order is brought forward, and none when that newer order was already brought forward, dispatched or delivered, or is for today or a day still to come. The reason names the day, for example *was entered again for 26 Sep (brought forward to 27 Sep)*. This way the customer never gets the line twice. If it really is a second delivery, add it as a late order;
- its day is **being optimized** right now: wait, then look again.

**Below the list (information, never ticked):**
- **Brought forward to (the day), not planned yet**, each with **Undo**: *Remove the copy of ACME on 6 Oct (40 cases)? The order goes back to the list.* Undo works only while no plan of that day holds the copy (not after OPTIMIZE or RE-PLAN planned it: a planned order cannot be removed in RouteIQ yet - ask an administrator).
- **Not delivered after it was brought forward**, for example *15 cases of GAMMA (T03 L1 stop 1, Customer refused) - add a late order for 6 Oct*: a result recorded after the order was brought forward made the shortfall bigger. An order is brought forward only once, so add the extra cases as a late order.
- **Dispatched, no result recorded (counted as delivered)**, per truck (*T05: 2 stops*): stops of loads that are back (an earlier day's, or today's that are Completed, back at the depot, or an hour past their planned return) without a result. They count as delivered; record their result on the plan of that day (**Record**) if they were not.

An order is brought forward **once**: after that it leaves the list, and clicking again (or two people at the same time) adds nothing twice. Once it was brought forward, the driver's page hides *Change result* on that stop (*Brought forward to 6 Oct*), and a change that would make the brought-forward cases fewer is refused (see *Delivery results*). A result changed while you were looking at the list makes Bring forward refuse and ask you to look again. If the list changed while you looked at it (for example a load was dispatched meanwhile), nothing is brought forward and you are asked to look again. An order of today is brought forward only when you ticked it under **Today**: if it is sent without that tick (for example from a screen opened before this change), nothing is brought forward and you are asked to tick today's orders yourself. The file of an order that was brought forward can no longer be deleted.

## Changing date or depot
While the new day loads, the screen shows *Loading ...* and its buttons are off; if it cannot be loaded, you see the error and **Try again** instead of the previous day. Everything you do (upload, confirm, optimize) is always for the day on the screen. If you change the date while a lock, OPTIMIZE, **Add … lines to the day** or a save is still running, it finishes for the day you started it on, and the screen then shows the date you picked. A **Check file** that finishes after you changed the date is not shown: check the file again for the day on screen. After **Add … lines to the day**, a file for another delivery date moves the screen to that date, unless you picked another date meanwhile.

## Driver shift (Settings, dispatchers and admins)
Dispatchers open **Settings** for the **Driver shift** card and the **Customer data before loading** card (see *Customer data: what to collect*: there you set the days ahead and see whether the loading rule is on; only a company admin switches the rule); everything else there is changed by a company admin. Every change is in the audit log.
- **First departure:** no truck leaves before this time. A plan made during the delivery day itself starts later: from now + the turnaround (see *Late orders*). Changing it keeps the **Latest return**; the shift maximum follows.
- **Latest return:** every truck is back at the depot by this time, whenever it leaves (also a truck that leaves late, or on a plan made during the day). It sets the **Driver shift maximum** (first departure to last return), and the other way round. A load planned with it that comes back later is blocked at Lock, Loading and Dispatch.
- **Overtime after:** from the first departure; at most the shift maximum.
- **Driver break, Break may start from, Break must start by:** the drivers' midday break (see *Driver break*). 0 min = no break.

**After this update is installed, set the company shift once:** First departure **07:00**, Latest return **18:00** (shift maximum 11 h). Leave **Overtime after** as it is. Set **Driver break** to **60** min, **Break may start from 12:00**, **Break must start by 14:00** (the break is off until you do). Plans already made keep the times and rules they were made with.

## Driver break

One driver per truck per day gets one break (60 min by default), **starting** between 12:00 and 14:00.
- RouteIQ plans it wherever the truck is at that time: between two stops (driving, or resting at a customer before or after unloading), or at the depot between two loads. Drivers do not load, so a depot break may run while the truck is being reloaded. It is **never** planned while unloading.
- The break is inside the shift (an 11 h day includes it). It is paid driver time and counts toward overtime.
- **No break is needed** for a truck that is back at the depot for good by 14:00, or whose first departure is at 12:00 or later.
- Time already spent before a plan is made does not count: a truck that stood at the depot from 12:10 gets its break from the time the plan is made, and after 14:00 it takes no new load that day unless it has had its break.
- The plan screen shows the break under the load (*break 12:40-13:40*) and as its own row between the stops (*Break 12:40-13:40 between stop 3 and stop 4*). Each stop also shows *unloading until* - when the truck must be finished there. The driver sheet, the Excel file and the WhatsApp message say the same.
- **A truck that needs a break and has none cannot be locked, loaded or dispatched** (there is no override): re-plan. Loads planned before this rule keep the rules they were planned with and are never blocked for it; a locked load flagged for it must be put back to Planned first. A load that has already left only shows a warning.
- If the locked or dispatched loads of a truck already run through 12:00-14:00 without a recorded break (planned before the rule), the plan says so; nothing can be added to them.


## Customer data: what to collect, and the daily customer master
The customer master is filled in as orders come: every customer with orders needs a **usable location** and its own **confirmed receiving hours** (or **Open all day**). Company and customer-type default hours do not count.

**1. The loading rule (Settings; only a company admin switches it).** The card **Customer data before loading** has:
- **Require location and delivery window before loading** (off until the company admin switches it on; a dispatcher sees *On* or *Off* and cannot change it, because it is management's control over loading): no truck is locked (and so never loaded or dispatched) while a customer on it has no usable location or no delivery window. A delivery window is the customer's own confirmed hours, or a delivery time set for its order (urgent or promised) that the plan was made with. You can still optimize and see the plan. Loads already locked, loading or out are never stopped by it.
- **Data to collect: days ahead** (default 3, 0 to 14): how far ahead the *Data to collect* list looks.

**2. See what is missing.** Step 2 of Daily dispatch has **Data to collect** (counts per depot, this depot's customers). The **Customers** page has the switch **Data to collect (N)**: only those customers, soonest delivery first, each with what it misses (*Location*, *Receiving hours*, or both) and its first delivery date.

**3. Send the list to whoever collects the data.** **Data to collect (Excel)** on the Customers page, or **Excel, this depot** on Daily dispatch. The first sheet lists each customer with what is missing, **what to do** (in plain words, per customer), the first delivery date, the depot, its address, the location status and the hours in use; the sheet **Per depot and day** gives, for each depot and day, the customers with orders and how many of them miss data. A customer whose code differs from another customer's only in letter case (*C001* and *c001*) is on the sheet **Same code, other case** instead, for reading only (the import would update the other one): set its data on Daily dispatch. The collector fills in, for each customer:
- `lat` and `lng`: the exact location, at least 4 decimals, typed as they really are (the two columns are already Text, so Excel keeps every digit). Or leave them empty and drop the pin later with **ADD LOCATION**.
- `hard_from`, `hard_to` (never outside) and / or `preferred_from`, `preferred_to`: the receiving hours, as 06:00 (24:00 = the end of the day). Or `open_all_day` = yes for a customer that accepts deliveries at any time.
- **Hours already shown in the file** are saved but not confirmed. If the customer says they are right, write `yes` in `hours_confirmed`. Left as they are with `hours_confirmed` blank, they stay **not confirmed** and the customer stays on the list.

**4. Import it back** (Customers > **Import CSV**; **Validate only** first). Hours you enter or change in the file are saved as **confirmed by you** (write `no` in `hours_confirmed` to save them without confirming); hours already shown are confirmed only with `yes` in `hours_confirmed`. A location is added only for a customer that has none or only one that cannot be used: **only an admin can change a saved location**, so a different location in the file is kept as it is and the import says so (a location confirmed on the map is never changed by any import, an admin's neither). A blank cell never removes anything, and a row that changes nothing writes nothing. **Use a fresh file:** a row whose customer was changed in RouteIQ after the file was downloaded (someone confirmed its hours, changed its name, ...) is not imported, so an old file never undoes a newer change; the import lists those customers - download a new file and enter their changes again.

**5. Download the customer master every day** (Customers > **Download customer master**, dispatchers and admins). One Excel with:
- **Customers**: every customer - code, branch, name, region and depot, type, priority (and whether confirmed), location with a Google Maps link and its status (who confirmed it, when, where it came from), its own receiving hours (whether confirmed, by whom, when) and the hours planning uses, unloading time, payment type, address, active, created and last changed.
- **Changed in last 24 hours** (or **Changed since** the date you pick, at most 31 days back): the customers created, changed or deleted since then, with when, by whom and what changed (a customer of **Same code, other case** says so).
- **Still missing**: the data-to-collect list.
- **Same code, other case** (only when there are such customers): older customers whose code differs from one on the **Customers** sheet only in letter case (*C001* and *c001*). For reading only: the import updates the one on the **Customers** sheet.
- **About this file**: what each column holds and which columns are imported back.

You can correct the **Customers** sheet and import it back the same way (step 4). Imported back without changes, it changes nothing. A location that is not usable is left blank in the file (drop the pin instead), and a customer's hours are shown only when they are its own (never a default).

## Settings (company admins)
Settings shows only what the planner uses, each with its unit and allowed range, and an **Effective planner values** table that says what the next optimization uses and where each value comes from. Saving sends only what you changed; if another admin changed the same setting since you opened the page, nothing is saved and you are asked to reload.
- **Costs:** driver cost per hour (paid for the whole truck day), overtime after (at most the shift maximum) and per hour (on top), fuel price per litre, preferred-window penalty. Truck costs (fixed per day, per load, per km, km per litre), max loads and availability are set per truck under **Trucks**; depot opening hours under **Depots**.
- **Country** is chosen from a list: it decides whether plans use road distances (Oman and the UAE) or straight-line estimates.
- **Default service time** is used for customers whose own unloading time was never confirmed (and whose customer type has none). A customer's page shows the unloading time the planner uses and where it comes from; to give a customer its own time, set it in the customer details on Daily dispatch. An amber note there means a time was stored for the customer but never confirmed, so it is not used. A customer created from an order file (or a late order) has no time of its own: under its customer type's time the page shows no note; without one it shows a grey line - set 10 min only if that customer really needs it.
- **Driver page and delivery results:** the **arrival radius** around a customer's pin (50-500 m, default 100) inside which the driver's page counts the truck as arrived; **photo required** for Delivered and Partly delivered (default on); how long **delivery photos** (30-1095 days, default 365) and **driver positions** (30 days up to the photo time, default 90; the distances from the pin stay) are kept; the **dispatcher phone** behind the driver page's *Call dispatcher* button (empty: no button). Lowering a time deletes older photos or positions for good at the next clean-up (RouteIQ cleans up every 10 minutes: photo pictures older than the photo time are removed, their record stays; positions, IP addresses and phone ids older than the position time are erased, the distances from the pin stay). Deleted data stays in the database backups until those expire.
- **Overtime after** must be at most the shift maximum when you change either of them. If an older setting breaks this, the page shows a note, and other settings still save.

### Dispatch timing (Settings → Daily dispatch: timing)
Set these to what the depot and drivers really do; every load is timed with them. The first departure and the shift are on the **Driver shift** card.

**Receiving hours:** unloading must be finished by the end of a customer's receiving hours. A customer whose unloading takes longer than its receiving hours is not planned (*Unloading takes 90 min, but the receiving hours 06:00-07:00 are only 60 min long*): correct the hours or the unloading time. Preferred hours work the same way: a penalty per minute that unloading starts before the preferred start or finishes after the preferred end.
- **Turnaround between loads (minutes):** fixed depot time between two loads of one truck (paperwork, queue). Default 30. It is also the preparation time of a plan made during the delivery day: no new load leaves before now + this + its loading time.
- **Loading minutes per case:** added to the turnaround for every case of the next load. 0.04 = 44 min extra for a 1,100-case load. Default 0. The first load of a day planned the day before is loaded before the first departure; on a plan made during the delivery day, loading counts from now for every truck, also one standing at the depot.
- **Unloading minutes per case:** added to each customer's service time for every case delivered. 0.05 = 55 min extra for a 1,100-case drop. Default 0. Each truck visit of a split delivery gets the customer's full unloading time plus the time of its own cases.
- **Max loads per truck per day:** default 3; a truck's own limit wins when it has one.

Changes apply to the next **OPTIMIZE** or **Re-plan**; plans already made keep their times.

## Signing in
- A session lasts one shift: after 12 hours you sign in again, even if you kept working. If your account is changed (deactivated, password reset, role changed) the change applies within a minute, and the sign-in page says "Your session has ended". After you sign in again you are back on the dispatch screen with the same day and depot (anything typed in an open dialog is lost).
- Forgot your password? Ask your company admin: on **Users**, **Reset password** gives you a new temporary password. ("Forgot your password?" on the sign-in page works only when reset email is set up; otherwise it says so.) If you also use a reset link from an email at the same moment, the admin's temporary password wins: the link then says it is invalid or has expired.
- A company always keeps at least one active company admin: an admin cannot deactivate or demote the last one, also when two admins try it on each other at the same moment (one of them is refused).
- After several wrong passwords, sign-in pauses for a few minutes; the message is the same as for a wrong password.
- The old driver phone app (`/driver`) is retired. Drivers get the **driver sheet** (PDF), the **WhatsApp** message from the plan and, since 4 Oct 2026, their own page through the **driver link** (QR) on the sheet: no sign-in for drivers.
- **Drivers are never deleted**: the button on the Drivers page is **Deactivate**. Past and planned loads keep the driver, and the driver stays the default driver of their trucks (the message names those trucks: choose another default driver under **Trucks**); new plans do not use an inactive driver. Reactivate with **Edit**.
- **Depots**: a depot that anything refers to (trucks, regions, plans, orders, order files) is **deactivated**, never deleted; the dialog says which will happen. Its orders keep the depot and wait until it is active again; they never move to another depot's plan. Orders and order files that had no depot before every order needed one were given a depot by RouteIQ; those it could not place are on a depot **NO-DEPOT** (*No depot (kept for history)*), shown as **History only**: it keeps them for the record, cannot be made active and cannot get trucks or regions.
- **Clearing a field**: emptying a driver's phone (or choosing **No depot** as a region's default depot) and saving clears it; a region can be created without a depot. On the **Trucks** page, *Available until* 00:00 means midnight.

## Good to know
- "Estimated km" means straight-line distances were used: the road-routing service was not available or too slow, or (on one load) a customer pin is far from any road. "Road km (3 legs estimated)" means most of the plan is on real roads but a few legs are estimates - usually a wrong pin: check those customers' locations. The plan is still valid, but check long trips. A reason "No truck can reach this customer ... (based on estimated distance)" rests on such an estimate.
- On the plan map a solid line follows the roads. A **dashed** line is only a straight line between the stops: the map could not get that load's road shape. While the map is still getting the road shapes it shows only the stops, with no lines. The text under the map says how many loads are dashed and why. When the cause is temporary (for example the routing service was restarting) the map tries once more by itself after a few seconds, and **Retry** asks again; if the routing service was only slow, press **Retry** yourself a little later. If the plan was changed meanwhile on another screen (for example another dispatcher pressed **Use instead**), the map notices, reloads the plan by itself and then shows its road shapes. Dashed lines change no km: the plan's km are what the plan shows ("Road km" or "Estimated km").
- Receiving hours and priority for many customers come from their **customer type**. Set the type once and the defaults apply.
- Everything you save (locations, priorities, hours) is kept on the customer master and in the audit log.
- Customer and product codes are the same whatever their letter case: `c001` and `C001` are one customer. A second one differing only in case cannot be created.
- **Customer import:** a column that is missing or a blank cell never erases what is saved (service time, region, address, payment type, location). A location a dispatcher confirmed on the map is never replaced by the file, also when it is confirmed while the import runs; the result says how many were kept. A location in the file that is not exact (fewer than 4 decimals, swapped, outside Oman/UAE, or 0,0) is not saved: a new customer has no location until you set one, and the result lists those rows with the reason. An existing customer keeps the location it has when the file points at the same place. When the file points somewhere else, its saved location is no longer used (the row says how far away the file points) until you put the pin on the shop with **ADD LOCATION**; a location confirmed on the map is never changed. When the saved location itself is not exact or is outside Oman/UAE and nobody confirmed it, the row says it is not used either. Until the pin is placed, their orders are not planned or sent out. Type or paste each coordinate with all the decimals it really has (at least 4). If Excel drops a trailing zero (23.5850 becomes 23.585), format the lat and lng columns as Text before you type or paste. Of the zeros at the end of a coordinate only one counts, in any file (a workbook, a Text cell, a CSV, whichever way the browser sends it), and in **ADD LOCATION** too: 23.5850 is 4 decimals, 23.5800 is 3, and the row says "Fewer than 4 decimals (only one zero at the end counts)." So do not fix a short coordinate by formatting the cells to show more decimals: 23.58 shown as 23.5800 is still only good to about 1 km, and it is not saved, also when you save the sheet as CSV (Excel writes each cell as it shows it). A real coordinate that ends in 00 needs its pin placed by hand, or more decimals in the file. A row listed as not exact whose customer keeps the location it already has (for example a list Excel saved again without a trailing zero) needs nothing: that customer is planned and sent out as before, and the result counts those rows on their own line. A service time in the file (at most 480 min) counts as confirmed for that customer. **Validate only** lists how many customers are new or updated and which confirmed service times would change.
- **Customers page:** switching *Active* or changing the priority shows at once. If RouteIQ refuses the change (not allowed, or not a valid value), the row goes back and the message says why: nothing was saved. If there is no answer (network) or the server answers with an error (for example during an update of RouteIQ), the change may or may not have been saved: the row then shows what the server has saved, and the message says so. If even that cannot be read, the row goes back and is marked **not confirmed**: reload the page to see what is saved. The change is never sent a second time by itself.
