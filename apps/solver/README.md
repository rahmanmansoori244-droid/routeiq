# RouteIQ Solver

FastAPI service, deployed separately from the web app. Every endpoint except `/health` requires the `X-Solver-Token` shared secret.

| Path | Engine | Purpose |
|---|---|---|
| `GET /health` | — | Railway health check |
| `POST /optimize-dispatch` | **OR-Tools** (`dispatch_solver.py` + `load_repack.py`) | NMWC daily dispatch planner: cases+kg capacity, hard + preferred windows, strict P1–P5 priorities, multi-load trucks (depot reload visits, turnaround per case), frozen locked/dispatched loads, RECOMMENDED + MIN_TRUCKS + MIN_DISTANCE; after the routing search a CP-SAT step re-assigns whole loads to trucks and every plan is timed exactly. A second route search, **PyVRP 0.14.0** (`pyvrp_candidate.py`), searches the same day in a process of its own; its plan is one more candidate that the engine's checks, timing and cost score judge |
| `POST /optimize-dispatch/stop` | — | a running THOROUGH solve (`config.search_mode`) returns the best plan found so far; 404 when none of that plan and company runs here, 409 for a QUICK solve |
| `POST /route-geometry` | OSRM | road polyline for a load (straight lines when unavailable) |
| `POST /optimize` | PyVRP (`solver.py`) | legacy v1 three-scenario solver, kept for comparison only |

Road distance comes from `providers.py`: OSRM when `OSRM_URL` (or the request's `osrm_url`) is set, and otherwise Haversine × multiplier labelled as estimated. There is no silent public default; see `../../docs/OSRM_SETUP.md`. Each matrix cell knows whether it is a road or an estimated leg (a pair OSRM could not route, a point more than `OSRM_MAX_SNAP_M` from any road); the truck factor `road_time_factor` applies to road cells only, and the response says `distance_quality` ROAD / MIXED / ESTIMATED with `estimated_legs` per load. Road routing has a deadline: `MATRIX_BUDGET_SEC` (default min(90 s, 20% of `SOLVER_BUDGET_SEC`)); after it the whole matrix is estimated, with a "road routing too slow" warning. `OSRM_TABLE_TILE` (default 90 coordinates per `/table` call; production can raise it up to the OSRM server's `--max-table-size`, 1000 in `infra/osrm`, so a day needs one call) and `OSRM_PARALLEL` (default 2, max 4 calls at once) tune the calls. At most 600 stops per request (422 above).

Costs (`costing.py`, one model for the score and the report): the driver is paid for the WHOLE truck day, from the first departure (or first frozen departure) to the last return, turnarounds and waiting included; overtime after `overtime_after_min` from that first departure is added on top. Each load carries its share (the paid time from the truck's previous return to its own return), so frozen loads + new loads = the day.

Search modes (29 Sep 2026): `config.search_mode` QUICK (default) searches the automatic time by day size within `SOLVER_BUDGET_SEC` (540 s), as before; THOROUGH gives the whole request up to `THOROUGH_MAX_SEC` (1200 s; `config.max_search_sec` may only lower it) and stops the recommended plan's search once it has not improved for max(`THOROUGH_STALL_SEC` 300 s, `THOROUGH_STALL_SHARE` 0.5 × the time searched so far). The response's `search` says how it searched and why it stopped. A request whose caller disconnects is cancelled within about a second (its worker processes stop, its slot frees). See `../../docs/OPTIMIZER_BENCHMARK.md` §11 and the handbook's 4.9.

## Local dev
```bash
python -m venv .venv && .venv/Scripts/pip install -r requirements.txt   # bin/ on Linux/macOS
# apps/solver/.env holds SOLVER_TOKEN (and OSRM_URL for a local OSRM); --env-file loads it.
# Inline variables still win: SOLVER_TOKEN=... .venv/Scripts/python -m uvicorn main:app --port 8000
.venv/Scripts/python -m uvicorn main:app --env-file .env --port 8000
# Smoke test: a wrong token answers 401 (a 500 "Solver not configured" means SOLVER_TOKEN was not loaded)
curl -s -o /dev/null -w "%{http_code}\n" -X POST http://localhost:8000/route-geometry -H "X-Solver-Token: wrong" \
  -H "content-type: application/json" -d '{"coords":[[23.6,58.4],[23.61,58.41]]}'
.venv/Scripts/python -m pytest tests -q
```

Every plan scenario runs in a worker process (OR-Tools holds the GIL, so an in-process search would freeze `/health` and every other request). `SOLVER_PARALLEL=0` runs every scenario inside the API process with no deadline and no time budget, for tests and debugging only (a warning is logged at startup; an error on Railway). Every returned option carries an independent timing check (`feasibility.py`, `DispatchScenario.feasibility`). Rule 22 (owner decision, 30 Sep 2026): the worker processes are started, and must run a first task within `SOLVER_WORKER_START_SEC` (30 s), before the road matrix is fetched; when they cannot start, `/optimize-dispatch` answers 503 `{"detail": "The planner is busy or restarting - try again in a minute.", "code": "WORKERS_UNAVAILABLE"}` within seconds, logs an ERROR line containing `WORKERS_UNAVAILABLE` (after the log's timestamp, level and logger name: alert with a substring match), and `/ready` reports `workers.status: failed` (`ok: false`) for at least 5 minutes, whatever pools start meanwhile, and at most 15. A pool that breaks during a solve (a worker killed with no replacement possible, or no process able to take a task any more) is noticed within seconds: a 503 the same way when the recommended plan's own worker stops and cannot be replaced, or its search cannot start; when another worker stops while the recommended search runs, the recommended plan is kept, the other options are skipped, and its loads are re-checked with fresh processes (or re-timed exactly when those cannot start). Closing a pool never holds a request for more than about 10 s (`POOL_CLOSE_SEC`) and never starts a replacement process. It never falls back to searching in-process, except with `SOLVER_ALLOW_INPROCESS_FALLBACK=1` (development and tests only; logged at startup, an error on Railway). Design notes: `../../docs/OPTIMIZER_DESIGN.md`.

The second route search (PyVRP, `docs/OPTIMIZER_BENCHMARK.md` §12): `SOLVER_PYVRP` = `on` (default) / `off` (or `0`) / `thorough`; `SOLVER_PYVRP_MIN_CPUS` (2) is its CPU gate; `SOLVER_PYVRP_SEED` (1); `SOLVER_PYVRP_STOP_GRACE_SEC` (10). Its process is optional: when it cannot start or fails, the engine alone answers and one log line says why. `/ready` reports `pyvrp` (enabled, version, effective CPUs, why not) and the startup log has one line. Local development: `SOLVER_PYVRP_MAX_ITERS=N` stops it after N iterations (reproducible), `SOLVER_PYVRP_STALL_ITERS` shortens its Thorough stall rule; the tests switch it off by default (`tests/conftest.py`).
